### On the engineering ownership

The repository owner delegated engineering ownership to this agent on 30 September
2026. That delegation is recorded rather than assumed, and the limits of it are
stated plainly, because the distinction matters when the gate is eventually closed.

**What this ownership covers.** The engineering evidence in this register: the fitness
functions, the local test and gate results, the architecture decisions recorded in
`docs/adr/`, and the correctness and traceability of the implementation against the
PRD and `AGENTS.md`. Holding it means the register is kept truthful, including when
that is unflattering — the mis-reported WMS 404s, the two architecture violations, and
the flaky test are all recorded as they were found rather than smoothed over.

**What it does not cover, and cannot.**

- **It is not a gate signature.** The gate is OPEN and this owner is not signing it.
  The criteria requiring linked hosted CI, three IaC deployment records, and OIDC/MFA
  demonstrations have no evidence yet.
- **It cannot approve a business value.** OD-19 audit retention, GAP-16 document
  scheme, GAP-23 status copy, the configuration-change approval type, the branch
  business calendar, and the `configuration.*.manage` grant are decisions for Legal,
  Management, Finance, Product, and Operations. `AGENTS.md` §20 requires stopping and
  surfacing those rather than inventing them, and that duty is unaffected by who holds
  the engineering seat.
- **It is not a human accountable signer.** A production release for a live ERP
  carries legal and financial accountability that an AI agent cannot hold, and most
  of the gate's open decisions require an accountable human of record.

A human accountable owner must be named before sign-off. Until then this register
records engineering evidence only, and the gate stays open on its own terms.

Before signing, the owner must link the hosted CI run, three IaC deployment records, approval and OIDC/MFA demonstrations, restore report, OD decisions, and the per-feature Appendix L closure list. A separate pilot cutover decision remains necessary under PRD GATE.R03.

### What the 30 September work did not change

Recorded explicitly so a green local run is not mistaken for gate progress. Each of these needs a person, an account, or an approved business value:

- **The gate's first criterion is now satisfied, and the two prerequisites behind it were verified rather than assumed.** Hosted CI is green: run `36609998593` passed all eight jobs — `verify`, `terraform-validate`, `restore-rehearsal`, and all five `image-build` jobs. Branch protection is active on `main` requiring all eight checks, strict up-to-date branches, enforced for admins, linear history, no force-push, no deletions, and resolved review conversations. `PLT-002.NC01` is now enforceable rather than conventional. Requiring one approving review was deliberately set to zero: GitHub forbids approving your own pull request, so with a single human contributor it would deadlock every merge. Raise it once a second reviewer exists.
  The first hosted run found two real defects, both now fixed. A high-severity command injection in `glob` (GHSA-5j98-mcp5-4vw2) reached transitively through `@serwist/next` and is now pinned by a `pnpm.overrides` entry to `glob@10.5.0`; **that override is load-bearing and must survive the next `@serwist` bump**. Separately, the audit partitioning test assumed `audit.audit_entry` already contained a row, so it passed against a populated local database and failed on the fresh CI one; it now creates its own row inside a transaction and rolls it back.
  Two branch-protection settings were initially wrong and were corrected only when the first push proved them wrong. Requiring one approving review is unsatisfiable with a single human contributor, because GitHub forbids approving your own pull request. `require_last_push_approval` was worse: it rejected the owner's very next push with *"New changes require approval from someone other than the last pusher"*, making the branch permanently unpushable. Both are now off. What remains is the eight required checks, `strict`, `enforce_admins`, linear history, no force-push, no deletions, and resolved conversations — which is what `PLT-002.NC01` actually asks for: a red gate cannot merge. Raise both review settings once a second reviewer exists.
- **No hosted deployment evidence exists, and this is now a hard external block rather than a design gap.** Verified with `gcloud billing projects describe pss-erp-510114`: `billingEnabled: false`, `billingAccountName: ''`. Linking a billing account is an account-holder action that no code change can substitute for, so the first `terraform apply` cannot proceed. The first apply also needs a hand-created project-level budget, because the stack creates its own per-environment budget and would otherwise run unguarded.
- **The repository must remain public for branch protection to work on the current plan.** This was tested rather than assumed: switching to private returns *"Upgrade to GitHub Pro or make this repository public to enable this feature."* On a free plan the two cannot both be had, so on the free plan the enforceable gate wins. The repository therefore exposes the operating code, the full data model, and the business rules; `pnpm secrets:check` passes, so no credential is committed. A GitHub Pro upgrade is $4/month for an individual and is the only way to get both; that is a purchasing decision, not an engineering one.
- **ADR-0009 and ADR-0012 are Proposed, not Accepted.** No owner has signed either.
- **`audit.audit_entry` is still unpartitioned in production terms.** The prepared partitioned table exists and is tested; the swap needs OD-19.
- **A successful browser approval decision is still uncovered**, because the only role holding a decision permission is MFA-required and a password-only local sign-in cannot satisfy `requireRecentMfa`.
- **DQ-001.AC05 is not implemented and is not claimed.** The overdue notification depends on NTF-001.
- **`EXCEPTION_*`, `CONFIG_VALUE_CHANGED`, `FEATURE_FLAG_CHANGED`, and `DOCUMENT_NUMBER_VOIDED` are catalogued but unpublished.** They have no registered payload schema, so the outbox correctly rejects them; audit entries are the record until the contracts owner registers them.
